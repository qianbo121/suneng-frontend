# 迁移备份与隔离恢复

用于官网上线前保存可恢复的独立基线。工具不会部署应用、切换域名或将备份写回生产数据库。

## 1. 范围与执行

运行位置是已盘点的官网主机：源码 `/opt/website`、数据库 `/data/postgres`、上传 `/data/uploads`。脚本先核对实际挂载，再以独立批次保存到 `/data/migration-backups/<批次>/`，不进入例行七天清理目录、不覆盖旧批次。

备份包含：

- 一致的数据库快照、各表记录数与内容指纹、上传文件及逐文件指纹。
- 运行中的前端、后台、后端、入口服务和数据库镜像；生产源码、环境配置、入口配置及证书配置。
- 程序版本、启动时间与实际挂载记录。敏感原始配置和容器完整信息只保存在受限备份目录。

批次标识格式为 `20260910T020814Z-15e358b4`，由执行时间加随机标识组成。新的备份必须生成新的标识；已有批次会被拒绝覆盖。示例中的 `$migration_batch` 必须是已核对的值：

```sh
# 在已确认的服务器上，使用已交付脚本建立备份。
python3 scripts/geo-migration/backup_rehearsal.py backup --id "$migration_batch"

# 将同一份备份恢复到临时实例和新的私有目录。
python3 scripts/geo-migration/backup_rehearsal.py drill --id "$migration_batch"
```

也可从本地将已审阅的脚本通过 SSH 标准输入执行，避免改动当前生产源码目录。本轮采用此方式。禁止在命令行或报告中输出备份内的密钥、客户信息和原始数据库内容。

备份期间不停止正常写入：数据库采用同一个只读事务快照，上传文件在前后两次核对内容不变。它是该时间点的演练基线；正式切换仍需短时停写或有证据的增量同步，不能把今天的基线当作以后上线当天的最终数据。

## 2. 恢复验收与失败处理

恢复使用当前生产 PostgreSQL 的同一镜像，在单独容器内新建数据库；只挂载本批次新目录，没有外部网络、没有对外端口，限制内存和 CPU。临时实例采用隔离的本地访问方式，不复制或改变生产数据库的认证配置。

实际验收包括：导入遇到错误立即退出；所有数据表记录数与内容指纹一致；139 等实际数量的上传文件逐个一致；程序归档中的运行平台、镜像身份、数据块和依赖完整；源码与配置关键文件存在。权限所属采用临时实例角色，未将它视为生产账号权限或整套业务验收。

同批次最多两次恢复尝试，第二次使用 `--attempt 2`，保留第一次目录和记录。临时实例只在名称、归属标记和网络隔离三项匹配时清理，生产容器不会成为清理目标。失败后的临时数据库日志保留在私有批次中。

若数据与文件已经成功恢复，只有归档身份校验或状态记录需要核对，可运行：

```sh
python3 scripts/geo-migration/backup_rehearsal.py verify --id "$migration_batch"
```

此命令重新核对归档、依赖和当前生产状态，单独保存 `archive-verification.json`，保留原尝试记录。镜像身份同时支持传统 Docker 清单及 OCI 索引；挂载比较忽略返回顺序，但不忽略路径、读写权限、版本、启动时间和健康状态。

本地回归：

```sh
PYTHONDONTWRITEBYTECODE=1 python3 scripts/geo-migration/test_backup_rehearsal.py
```

## 3. 保存和生产回退边界

备份目录权限为 700，备份文件为 600。备份包含客户信息、环境密钥和证书私钥，不能放进 Git、前端 public 目录或公开报告。复制到另一设备时，要先明确授权目的地，并逐个核对复制前后指纹；本轮本机第二份备份尚待用户明确保存位置授权。

保存成功和隔离恢复成功，不代表已经演练整站切换。实际程序替换、业务兼容、询盘收发、网站入口及最终增量同步需按上线前验收单进行。

生产回退遵守根目录 DEPLOY.md 第 4.2 节：新版询盘开放后，优先修复，必要时仅回退前端展示／表单，保留新版后台、后端、数炬和新增数据。不得将旧数据库覆盖到当前库、不得照抄整体旧版本回滚；新增询盘与文件要先导出并逐条对账。执行生产切换或回退需要对应的发布授权。
